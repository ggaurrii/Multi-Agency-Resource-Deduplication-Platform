1. Introduction
1.1 Purpose
This System Design Document (SDD) translates the requirements defined in SAHAYOG_SRS.docx v1.0 into a concrete technical design: system architecture, database schema, module-level design, API contract, and a sprint-wise development roadmap. It is the primary reference for implementation and code review.
1.2 Scope
This document covers the design of the SIH MVP (flood-relief scenario: 4 districts, 3 agency types, 5 resource types) and notes, where relevant, extension points for the full system vision described in SRS Section 6. It does not restate functional requirements in full — refer to the SRS for the authoritative requirement list (FR-xxx / NFR-xxx IDs used below match the SRS).
1.3 Design Goals
Correctness of the deduplication and matching logic over visual polish.
Clear separation between the optimization/forecasting logic and the API layer, so algorithms can be swapped without changing contracts (supports SRS Section 5.4, Maintainability).
A data model that treats resource_type and disaster_type as configurable values rather than hard-coded enums, so new disaster scenarios can be added without schema migration (supports SRS Section 6).
A human-in-the-loop authorization step before any resource is marked IN TRANSIT (supports SRS Section 5.2, Safety).
2. System Architecture
2.1 High-Level Architecture
SAHAYOG follows a layered pipeline architecture. Agency users submit data through a common API Gateway; that data flows through the Deduplication Engine, then the Matching & Optimization Engine, then the Priority & Forecasting module, before recommendations and live status reach the Command Centre Dashboard. Authorization actions from the dashboard flow back through the same gateway.

2.2 Deployment / Component View

4. Module-Level Design
4.1 Deduplication Engine
Implemented as a database view / materialized aggregation rather than an application-level loop, for correctness and performance: GROUP BY (district_id, resource_type) over resource rows where status = 'AVAILABLE', summing quantity. Recomputed on every write via a trigger-backed refresh or a short-interval scheduled job (satisfies FR-DED-01/03).
Conflict detection (FR-DED-04/05/06) runs as a separate scheduled job comparing recent resource/need writes within a configurable time and geography window and inserting Notification rows when thresholds are crossed.
4.2 Matching & Optimization Engine
A stateless service function: given a need_id, it (1) queries candidate resources of matching type and AVAILABLE status within a search radius, (2) computes distance via PostGIS ST_Distance, (3) builds a constrained allocation problem — minimize total distance-weighted cost subject to not exceeding each resource's available quantity and meeting the need's quantity — solved with OR-Tools' CP-SAT solver for the MVP scale, falling back to a greedy nearest-first heuristic if the solver times out. Output is a proposed Allocation + AllocationItem set with status PROPOSED, never auto-committed (FR-MAT-01–05).
4.3 Priority & Forecasting Module
Priority (FR-PRI-01) is a pure function of a need's deadline, recalculated on read/write — no ML needed. Forecasting (FR-FOR-01/02) uses a lightweight linear regression / moving-average model over simulated historical consumption per (district, resource_type), producing an estimated_depletion_time; when this falls under a configurable threshold, the module creates a synthetic "pre-emptive" need feeding into the same matching pipeline.
4.4 Access Control Middleware
A FastAPI dependency validates the JWT, loads the user's role and agency_id, and injects a scope object used by every route handler to filter queries (e.g., Agency Staff can only UPDATE resource rows where resource.agency_id == user.agency_id). This mirrors the requirement that authorization is enforced server-side, not just in the UI (NFR-SEC-02).
4.5 Real-Time Update Service
Uses PostgreSQL LISTEN/NOTIFY triggered by row-level changes on resource, need, and allocation tables; the WebSocket service subscribes to these channels and rebroadcasts scoped events to connected dashboard clients over authenticated WSS connections (FR-RT-01/02). Clients reconcile state via a REST fetch on reconnect if a gap is detected (FR-RT-03).
